# AI 脚本生成模块需求文档

> 版本：v1.0（2026-10-22 初稿）
> 关联文档：`docs/requirements/AI脚本分析模块.md`（大模型接入配置、chat 调用链路复用来源）、`docs/features/ai.md`（Prompt 设计来源）
> 模块定位：在「添加脚本」弹窗内提供 AI 生成脚本草稿能力，用户用自然语言描述需求，AI 生成完整脚本并自动填充名称、描述、脚本内容三个字段，与现有「AI 分析」形成「AI 写 → 用户审 → AI 审」闭环。

---

## 1. 背景与目标

目前脚本管理模块已具备「AI 分析」能力（对既有脚本做安全与健壮性审查），但脚本的生产仍完全依赖人工编写。对于常见运维场景（日志清理、巡检采集、服务重启等），用户往往只需要一段几十行的标准 bash 脚本，从零手写效率低且容易遗漏防护措施（`set -euo pipefail`、变量判空、幂等处理等）。

本模块通过复用现有大模型接入通道，让用户在「添加脚本」弹窗内用一句话描述需求，AI 直接生成生产级脚本草稿并自动填充表单，用户审查修改后保存入库。

核心目标：

1. 入口位于「添加脚本」弹窗内，不新增页面、不新增弹窗层级；
2. AI 生成结果自动填充**脚本名称、脚本描述、脚本内容**三个字段；
3. 生成结果为草稿，**不落库、不缓存**，用户点「创建」后才进入脚本库；
4. 生成后自动联动现有规则引擎风险徽标（RiskAnalyzer）刷新，本地评估零消耗；
5. 完全复用现有大模型接入配置与安全策略（safeStorage 加密、内网 http 放行、token 统计）。

## 2. 已确认的决策（2026-10-22 需求沟通）

| 决策项 | 结论 |
| --- | --- |
| 入口形式 | 弹窗内嵌面板（脚本内容区标题行展开），不做「手动编写 / AI 生成」Tab 模式切换 |
| 填充策略 | **直接覆盖**名称、描述、脚本内容三个字段，不弹确认（用户明确选择） |
| 编辑模式入口 | 暂不提供（「AI 优化现有脚本」留二期，需传入现有内容做上下文，Prompt 复杂度高） |
| 目标系统选项 | 不提供固定选项（通用/CentOS/Ubuntu 等），目标环境、特殊要求完全由用户在需求描述里自行写明 |
| 结果缓存 | 不缓存。生成是一次性调用，同一需求可反复点「生成」重新调用（每次消耗 token） |
| 流式输出 | 不启用 SSE，整体返回后统一解析 JSON（与分析链路一致） |
| 生成后自动 AI 分析 | 不自动触发。本地 RiskAnalyzer 徽标自动刷新（免费即时）；是否花 token 跑 AI 分析由用户手动点已有「AI 分析」入口 |

## 3. 功能设计

### 3.1 入口与界面

「添加脚本」弹窗（`createScriptEditorDialog`，非编辑模式）的脚本内容区标题行增加「AI 生成」按钮，点击后在脚本内容输入区**上方**展开内嵌面板（不新开子弹窗，避免层级过深）：

```
脚本内容 * [普通]   [✨ AI 生成]              ☑ 显示预览
┌─ AI 生成面板（点击按钮展开/收起）─────────────────────┐
│ 用一句话描述你要的脚本，目标系统、路径、特殊要求等直接写明：│
│ ┌────────────────────────────────────────────────┐ │
│ │ 例：清理 /data/logs 下超过 7 天的 .log 文件，    │ │
│ │ 删除前统计每个文件大小并输出汇总，CentOS 7 环境   │ │
│ └────────────────────────────────────────────────┘ │
│                                        [取消] [生成] │
└────────────────────────────────────────────────────┘
[脚本内容 textarea（现有）]
```

面板细节：

- **需求输入框**：多行 textarea，必填，限长 2000 字符（超长提示并阻止提交）；
- **「生成」按钮**：点击后变为 loading 态（文案「生成中…」），期间需求输入框与生成按钮禁用，保存/取消按钮保持可用（用户可放弃）；
- **「取消」**：收起面板；需求文本在弹窗生命周期内保留（误点收起后再展开不丢内容）；
- 面板展开/收起状态不持久化，关闭弹窗即重置；
- 占位示例文案仅作提示，不预填入输入框。

### 3.2 填充行为

生成成功后：

1. **直接覆盖**以下三个字段（无论是否已有内容，不弹确认）：
   - `#scriptName` ← 生成结果 `name`
   - `#scriptDescription` ← 生成结果 `description`
   - `#scriptContent` ← 生成结果 `content`
2. 填充后自动联动现有逻辑（复用编辑器已有的 input 事件处理，或直接调用 `updateRiskBadge()` 与预览刷新）：
   - 规则引擎风险徽标（RiskAnalyzer）即时重新评估；
   - 若已勾选「显示预览」，语法高亮预览同步刷新；
3. 面板保留需求文本，显示轻量提示「已填充，可调整需求后重新生成」；
4. 名称/描述字段被覆盖时给予一次 toast 提示（如「已按 AI 结果覆盖名称与描述」），仅提示不阻断。

重新生成：用户修改需求文本后再次点「生成」，同样**直接覆盖**三个字段。

### 3.3 生成 Prompt 设计

新增 `buildGenerateMessages(requirement)` 纯函数（无 electron 依赖，可独立测试，与分析模块的 `buildMessages` 同级）。

**System Prompt 要点**：

- 角色：资深 Linux 自动化运维工程师，为生产环境编写 Bash 脚本；
- 强制工程规范：
  - `#!/bin/bash` 开头 + `set -euo pipefail`；
  - 变量引用一律双引号包裹，关键路径变量用 `${VAR:?提示}` 判空防护；
  - 幂等可重跑（重复执行不产生副作用）；
  - 可配置项（路径、阈值、保留天数等）集中为脚本头部变量并加中文注释；
  - 关键步骤输出执行日志（echo 带步骤说明），失败时错误信息明确；
- 安全约束：需求涉及破坏性操作（删除、kill、重启服务、覆盖文件等）时，必须内置防护（路径白名单、判空、操作前输出影响范围清单），不得生成裸 `rm -rf` 类无防护代码；无法安全实现的需求（如格式化磁盘）应在 description 中明确标注风险而非直接实现；
- 输出约束：严格按 JSON Schema 返回，不得输出 JSON 之外的任何自然语言。

**User Prompt 模板**：

```text
请根据以下需求编写一个生产可用的 Bash 脚本：

【需求描述】
{{REQUIREMENT}}

请严格按照以下 JSON 格式返回：
{
  "name": "英文脚本文件名（kebab-case，以 .sh 结尾，如 fix-data.sh）",
  "description": "简短核心描述（30字以内，只讲脚本做什么）",
  "content": "完整 Bash 脚本文本（含 shebang、set 选项、中文注释）"
}
```

> 脚本名称为**英文文件名格式**：kebab-case 小写英文单词加连字符，以 `.sh` 结尾（如 `fix-data.sh`、`clean-expired-logs.sh`），不用中文名；主进程另有 `normalizeGeneratedName()` 兑底规范化（非法字符转连字符、统一补 `.sh` 后缀，全非法时回退 `script-<时间戳>.sh`）。
> 描述字段定位为简短扼要：只讲脚本做什么，控制在 30 字以内；适用环境、风险提示等补充说明一律写入脚本文本的头部注释，不进 description。

### 3.4 生成调用（主进程 `aiService.js` 新增方法）

```js
/**
 * AI 生成脚本草稿（一次性调用，不落库、不缓存）
 * 返回 { success, data: { name, description, content }, usage, message }
 */
async generateScript({ requirement }) { ... }
```

处理规则：

1. 校验 `requirement` 非空、不超过 2000 字符；
2. `buildGenerateMessages(requirement)` 组装消息；
3. 复用 `this.chat()` 调用（沿用现有配置、超时 180s、非流式）；
4. 复用 `parseAnalysisJson()` 做 JSON 容错解析（剥围栏 → parse → 截取大括号重试）；
5. 校验解析结果：`content` 非空且不超过 30000 字符、`name` 非空；字段缺失或超限时返回明确错误信息；
6. token 消耗计入 `_addUsage()` 累计统计（与分析共用累计值；是否单列「生成」类统计见 §6 后续优化）；
7. 未配置大模型（Base URL / 模型 / Key 缺失）时返回与现有分析一致的引导错误（「请先在 设置 → 大模型接入 中配置…」）。

### 3.5 IPC 通道与前端封装

| 层 | 内容 |
| --- | --- |
| 主进程 | `main.js` 注册 `ipcMain.handle('ai:generateScript', (e, payload) => aiService.generateScript(payload))` |
| 渲染进程服务 | `src/renderer/js/services/aiService.js` 新增 `generateScript(payload)` invoke 封装 |
| 渲染进程 UI | `scriptManagement.js` 的 `createScriptEditorDialog` 内实现面板渲染与交互逻辑 |

### 3.6 数据流

```
添加脚本弹窗（scriptManagement.js）
    │ 点击「AI 生成」→ 展开面板 → 输入需求 → 点「生成」
    ▼
services/aiService.js → ipcRenderer.invoke('ai:generateScript')
    ▼
主进程 aiService.generateScript()
    ├── buildGenerateMessages() 组装 Prompt
    ├── chat() → OpenAI 兼容 /chat/completions（非流式）
    ├── parseAnalysisJson() 容错解析
    └── _addUsage() 累计 token 统计
    ▼
返回 { name, description, content }
    ▼
渲染进程直接覆盖 #scriptName / #scriptDescription / #scriptContent
    ├── 自动触发 updateRiskBadge()（本地规则引擎，零消耗）
    └── 预览刷新（若已开启）
    ▼
用户审查/修改 → 点「创建」→ 走现有 saveScript() 流程入库
```

## 4. 边界与异常处理

| 场景 | 处理 |
| --- | --- |
| 未配置大模型 | 生成按钮可点击，调用后 toast 展示引导文案（与分析入口一致），不报未知错误 |
| 需求为空 / 超过 2000 字符 | 前端拦截提示，不发起调用 |
| 请求超时（180s） | toast 展示「请求超时（180s）」，按钮恢复可用 |
| 网络失败 / Key 无效 / 模型不存在 | toast 展示主进程透传的具体错误信息 |
| 模型返回非合法 JSON | 容错解析三层尝试后仍失败 → toast「模型未返回合法结果，请调整需求后重试」；不填充任何字段 |
| 返回 content 为空 / 超 30000 字符 | 拒绝填充并提示具体原因 |
| 生成期间用户关闭弹窗 | Promise 结果丢弃（渲染层判断弹窗已移除则不再操作 DOM），无泄漏 |
| 生成期间重复点击「生成」 | loading 态下按钮已禁用，天然防重 |
| 生成内容包含高危操作 | 不做前置拦截——填充后规则引擎徽标即时亮红提示，由用户自行审查；保存与执行环节的强确认机制沿用现有链路 |
| 编辑脚本弹窗 | 一期不展示 AI 生成入口（仅添加模式渲染面板） |

## 5. 技术实现要点

| 项 | 方案 |
| --- | --- |
| 主进程 | `src/main/aiService.js`：新增 `buildGenerateMessages()` 纯函数与 `generateScript()` 实例方法，导出 `buildGenerateMessages` 便于测试 |
| IPC | `src/main/main.js` 注册 `ai:generateScript` 单条 invoke 通道（无事件推送，一次请求一次响应，无监听器泄漏风险） |
| 前端服务 | `src/renderer/js/services/aiService.js` 新增 `generateScript()` |
| 前端 UI | `src/renderer/js/scriptManagement.js` `createScriptEditorDialog()`：脚本内容标题行加按钮，弹窗内实现面板（复用现有 form-control / btn 样式，无新组件依赖） |
| 样式 | `src/renderer/css/components.css` 少量新增（面板容器、提示文案样式），遵循现有 tokens |
| token 统计 | 复用 settings.ai 累计字段；单次 usage 不落库（无缓存表交互） |
| 数据存储 | **零新增表、零 schema 变更**（草稿不落库） |

## 6. 后续优化方向（本期不做）

1. **单列生成类 token 统计**：settings.ai 中区分「分析」与「生成」两类累计值，设置页分开展示；
2. **编辑模式 AI 改写**：编辑弹窗中把现有脚本内容作为上下文传入，实现「AI 优化现有脚本」；
3. **流式输出**：长脚本生成耗时较长时，SSE 逐段回显提升体验；
4. **生成历史**：最近 N 次生成记录本地留存，方便找回误覆盖的草稿；
5. **多轮迭代**：基于上一次生成结果追加修改指令的对话式生成。

## 7. 验收标准

1. 「添加脚本」弹窗展示「AI 生成」按钮，点击展开面板；「编辑脚本」弹窗不展示该入口；
2. 需求为空时点「生成」被拦截提示，不发起网络请求；
3. 生成成功后名称、描述、脚本内容三个字段被直接覆盖填充（含用户已手动填写内容的场景，无确认弹窗）；填充的脚本名称为英文 kebab-case + `.sh` 后缀格式（如 `fix-data.sh`）；
4. 填充后风险徽标立即按新内容重新评估（本地规则引擎），预览（若开启）同步刷新；
5. 生成失败（未配置 / 超时 / 网络错误 / 解析失败）时有明确 toast 提示，表单字段保持原值不被破坏；
6. 生成过程中需求文本保留在面板中，可修改后重新生成；
7. 生成调用的 token 消耗计入设置页与状态栏的累计统计；
8. 用户点「创建」保存的脚本与手工创建的脚本在脚本库、执行、导入导出等链路中行为完全一致（无额外标记字段）；
9. `node --check` 语法通过，未配置模型时各入口给出明确引导。
