# 修复四项数据与执行缺陷

## 背景
上一轮已逐条核实四个问题均属实，本计划按 P0 → P1 顺序修复，全部为后端改动，不动 UI。

## 1. 批量移动目录 ReferenceError（P0）
- `src/database/models.js` `ScriptModel.batchMoveCategory`：`{ category_id }` 改为 `{ category_id: categoryId }`。

## 2. ID 复用与删除级联清理（P0）
### 2a. 持久化自增序列 — `src/database/simple-db.js`
- `DEFAULT_DATA` 增加 `_sequences: {}`（每表一个只增不减的水位）。
- `insert` 自动生成 ID 时取 `max(_sequences[table] || 0, 表内现存最大数字ID) + 1`，并回写水位；显式传入数字 ID 时同样抬升水位。
- 与现存最大值取 max 可自愈：旧数据文件、导入/恢复（`replaceAllData`）无需迁移脚本，首次插入即对齐。

### 2b. 删除主机级联清理 — `models.js` `HostModel.delete`
- 遍历 `task_executions`：从 `host_ids`（JSON 字符串，宽松比较数字/字符串）移除该主机；若 `scheduled` 任务主机列表被清空，置 `status='cancelled'`、`total_hosts=0`，避免调度器继续触发。
- 遍历 `project_steps`：同样从 `host_ids` 移除该主机（空列表步骤执行时会报"无目标主机"，不会再错配到新主机）。

### 2c. 删除工程级联清理 — `models.js` `ProjectTaskModel.delete`
- 现有级联删 `project_steps` 基础上，追加删除 `project_executions` 中该工程的记录（含 scheduled 残留），并按 execution_id 级联删 `project_step_executions`（实现前先确认该表关联字段）。

## 3. 重试策略区分失败类型（P1）— `src/main/taskExecutor.js`
- 重试循环中：脚本真实执行后返回非 0（`exitCode >= 0`）→ 视为业务失败，**不重试**直接结束；仅连接/执行异常（`exitCode === -1` 或 throw）才走指数退避重试。
- 支持 `options.retryTimes`（0 = 关闭重试），缺省沿用 `this.retryTimes`（3）。
- `src/main/taskScheduler.js` `executeScheduledTask` 与 `main.js` "立即执行定时任务" IPC：透传 `parameters.retryTimes`。

## 4. 破坏性命令检测与后台执行（P1）— `src/main/sshService.js`
### 4a. `isDisruptiveCommand` 重写（保持签名，taskExecutor 也在用）
- 逐行处理：先剥离引号内字符串与 `#` 注释，再按 `;`、`&&`、`||`、`|` 拆分命令段。
- 仅当命令段以破坏性命令开头才命中（允许 `sudo`/`nohup`/`env` 前缀）：`shutdown/reboot/poweroff/halt`、`init 0|6`、`systemctl reboot|poweroff|halt`。
- 效果：`last reboot`、`# 不要 shutdown`、`echo "reboot"` 不再误判；`sudo shutdown -h now`、`foo && reboot` 仍命中。

### 4b. nohup 分支修正（executeScript  disruptive 分支及 catch 兜底分支）
- 尊重 `options.useSudo`（拼接 sudo 前缀）。
- 日志文件名随机化：与临时脚本同基名 `.log`，替换固定的 `/tmp/shutdown.log`。
- 提交后 best-effort 回读日志开头（连接断开则忽略）， stdout 明确标注"⚠ 已后台提交，无法确认实际执行结果 + 远程日志路径"，并返回 `submittedOnly: true` 标记；不再伪装成拿到真实输出的"成功"。
- catch 中"破坏性命令 + 连接断开 → success"的兜底同样改为 submittedOnly 语义。

## 测试计划
1. `node --check` 校验全部改动文件语法。
2. 临时验证脚本（跑完即删）：
   - stub electron 后实例化 SimpleDatabase：插入→删最大 ID→再插入，断言 ID 不复用；显式 ID 插入后水位抬升。
   - `isDisruptiveCommand` 用例矩阵：误报样例（last reboot / 注释 / echo 字符串）返回 false，真实破坏命令（含 sudo、&& 组合）返回 true。
3. `GetProblems` 检查改动文件无 lint/编译错误。

## 假设与边界
- 不新增 UI 状态：submittedOnly 结果在任务侧仍记为 success（exitCode 0），但 stdout/error_message 带醒目"无法确认结果"说明，避免引入新状态的前端连锁改动。
- 历史数据中已存在的悬空 host_ids 不做一次性扫描修复（删除时清理 + ID 不再复用已阻断新增错配）；如需清洗存量可后续单独做。
- 破坏性分支仍跳过远程临时脚本清理（主机可能已关机），随机文件名避免覆盖。
